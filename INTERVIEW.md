# Interview notes - docs-search-mcp

Answers describe what this repository actually does.

## 10 likely questions
1. **What is MCP and what does this server do?** MCP is an open protocol that lets AI apps discover and call a server's tools over JSON-RPC. My server exposes five read-only tools: list/search/read local notes, fetch a web page as markdown, and convert times between timezones.
2. **stdio vs HTTP transport?** With stdio the client launches the server as a subprocess and uses stdin/stdout, so the server must never print to stdout. I log to stderr. `--transport streamable-http` runs it as a network server instead.
3. **How does the model know how to use a tool?** From the tool list: name, docstring-derived description and JSON Schema generated by FastMCP from the type hints. I wrote descriptions to say when to use each tool (e.g. "use read_note afterwards").
4. **How do you prevent path traversal in `read_note`?** I join the user path to the root, call `resolve()` (which follows symlinks), and require the result to be under the root, with an allowed suffix. Symlinks aren't indexed either. Tests cover `../`, absolute paths, wrong extension, and a symlink pointing outside.
5. **What is SSRF and how do you mitigate it in `fetch_url`?** A model-controlled URL could make the server request internal services such as `169.254.169.254` or localhost. I allow only http(s), resolve the host and reject any non-global IP, and repeat the check at every redirect (redirects are followed manually, max 3). Limitation: DNS rebinding between my check and the actual connection is not fully closed.
6. **How are errors handled?** Domain errors (`NotesError`, `FetchError`, `TimeError`) are converted to `ValueError`, which FastMCP returns as `isError` tool results. A test shows the server stays alive afterwards.
7. **How does search work?** At startup notes are split into sections by markdown headings; BM25 (k1=1.5, b=0.75) ranks sections for the query terms; the result includes a snippet around the first matching term.
8. **What did you change from the upstream `time` server?** Optional date so DST is computed for that day, and explicit handling of nonexistent (spring-forward) and ambiguous (fall-back) times. Upstream always used today's date.
9. **How did you test an MCP server?** Unit tests per module, a local `http.server` for the fetch tool (pagination, robots.txt, redirects, size cap, SSRF), and a protocol test that spawns the server and talks to it with the official `mcp` client: list tools, check annotations, call tools, check error handling.
10. **How would you use it with Claude Desktop, and what are the risks?** Add the command to the client's MCP config. Risks: `fetch_url` is an open-world tool, so prompt injection from fetched pages can influence the model; read-only annotations are hints; I haven't tested in Claude Desktop itself.

## 5 areas to study further
- The MCP spec: resources, prompts, sampling, authorization for HTTP transports
- SSRF/DNS-rebinding defences (pinning resolved IPs, egress proxies)
- Prompt injection through tool results and how clients mitigate it
- Embedding-based search and when BM25 is enough
- Async Python and how FastMCP runs sync tools

## Design decisions
- **FastMCP over low-level `Server`:** less boilerplate, schema from type hints; trade-off is less control.
- **Read-only tools only:** smaller blast radius and nothing to confirm.
- **Index at startup:** simple and fast for small folders; no reindex until restart.
- **Stdlib where possible** (robotparser, BM25 by hand) to understand the mechanics.
- **Fail closed:** unreachable robots.txt, non-public IP, unknown path → refuse.
